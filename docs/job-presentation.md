# 投递与面试展示

截至2026年10月23日，对外名称使用 **故障工单后端与自动化验证**；GitHub 仓库名保留 `incident-ticket-backend`。这是同一个个人项目，以下两种表述按岗位择一使用，不拆成两个项目。

项目使用 AI 辅助开发与验证，账号、故障和处理结果均为模拟数据。下面描述的是当前代码和验证结果；本人是否能够独立解释、修改和复验，需要通过文末演练确认。

## 投 Python 后端时

**故障工单后端与自动化验证｜个人项目，AI 辅助开发**

技术：Python、Flask、SQLite、pytest。

- 基于 Flask 和原生 sqlite3 实现工单创建、分页查询、状态筛选及“待处理→处理中→已解决”的完整流程；处理结果与解决人随最终状态在同一事务中保存。
- 实现会话登录、密码哈希和 CSRF 校验，区分提单人与处理人；列表和详情均限制数据可见范围，使用统一 JSON 错误及参数校验拒绝非法请求，通过请求编号关联响应与后台日志。
- 通过167项 pytest 测试，并以32次真实本机 HTTP 请求完成13组流程检查，验证越权拒绝、非法状态不改数据，以及重建应用后结果仍可读取。

展示时优先解释状态规则、数据库事务和权限如何生效。测试数量是本次运行记录，包含参数化用例，不等于167种独立业务能力。

## 投测试开发时

**故障工单后端与自动化验证｜个人项目，AI 辅助开发与测试**

技术：Python、pytest、Flask 测试客户端、SQLite、标准库 HTTP 客户端。

- 围绕工单完整流程组织正常路径、边界输入、身份权限、状态流转和数据一致性测试；使用独立临时数据库和客户端会话隔离数据，167项 pytest 测试通过，并可输出 JUnit XML 报告。
- 通过 SQLite 触发器和延迟外键约束分别模拟语句执行与事务提交失败，验证通用500响应、数据回滚、成功日志不误报及移除故障后的恢复；保留超长工单编号缺陷的复现、原因分析和回归用例。
- 编写可重复运行的真实 HTTP 验收脚本，自动调用初始化命令、准备三个模拟账号，完成32次请求、13组检查，并在重建应用后核对持久化结果，结束后关闭临时服务。

展示时选一个用例解释测试依据、预期结果和数据库断言，避免只展示“全部通过”。数据库故障属于人为注入的模拟演练；超长编号案例来自本项目本地开发，不是生产事故。

## 五分钟展示顺序

1. **0:00—0:30：说明场景与边界。**内部软件故障由提单人上报、处理人解决；个人项目、模拟数据、AI 辅助完成。打开 README 说明已实现的范围。
2. **0:30—1:30：运行完整流程。**按 README 设置 `$python` 后，在项目根目录执行 `& $python scripts/demo_workflow.py`，展示成功摘要，解释创建、可见性隔离、状态推进、处理结果和重启读取。
3. **1:30—2:30：解释一条关键规则。**打开 `ticket_backend/tickets.py`，说明为什么不允许待处理直接解决、谁可以修改状态、如何同时保存状态与处理结果，以及失败时数据库应保持什么状态。
4. **2:30—3:30：展示验证证据。**打开 `tests/test_ticket_workflow.py`，选择非法状态零修改或数据库故障恢复用例，讲清准备数据、发请求、检查响应及数据库四步。完整测试方法与本次结果见[验证记录](verification.md)。
5. **3:30—5:00：讲排查与限制。**按[问题排查案例](troubleshooting.md)说明超长编号的现象、路由转换阶段原因、修复及回归；最后说明当前没有知识检索、模型接入、持续集成或公网部署。

提前在本机完整演练一次。真实 HTTP 脚本自动使用随机端口和临时 SQLite 文件，不需要先开启开发服务；它验证功能，不提供吞吐量或响应延迟结论。
