`tests/test_observability.py` 验证服务端请求编号不采信客户端输入、连续请求编号不同，成功和400／401／403／404／405／413／415／500响应保留编号和 `no-store`，原 JSON 结构与405的 `Allow` 头保留。认证查库阶段失败也能通过编号关联错误与完成日志；状态更新成功日志使用同一编号。日志检查覆盖不记录请求体、查询值、密码、令牌和 Cookie，以及路径长度限制和控制字符转义。

## 状态历史与本地知识回归

[test_ticket_history.py](../tests/test_ticket_history.py) 验证新工单历史为空、两步成功更新记录实际处理人、前后状态、UTC 时间及响应请求编号；提单人只能读取自己工单的历史。历史写入触发器失败时状态更新一起回滚，移除故障后只增加成功记录。重复初始化保留数据，旧版数据库新增历史表不会编造过去的事件。竞争更新用例另确认只有成功者留下记录，失败请求编号不进入历史。

[test_knowledge.py](../tests/test_knowledge.py) 使用仓库6篇示例资料及独立临时文件，验证以下行为：

- 重复导入不增数据；修改文件后替换片段，旧片段编号不会指向新内容；目录少文件不自动删除旧资料。
- 文件名、大小、数量、UTF-8、标题及行长度限制，坏文件或数据库故障导致整批不写入，移除故障后恢复。
- 已知问题查到预期来源；空语料、无答案和关键词相近但无关的问题返回 `insufficient_evidence`。
- 返回的原文片段、文档标题、行号及 SHA-256 与存储原文一致，包含 CRLF 和多片段情形。
- 查询参数与编号边界、重复参数、登录限制；工单关联检索沿用工单可见范围，并报告超过500字符时的截断。

检索使用中文相邻双字和 ASCII 词项的词法匹配与排序，并有覆盖度及显式错误码检查。分数用于候选排序，不是正确概率，也不能保证匹配文档足以回答问题。
